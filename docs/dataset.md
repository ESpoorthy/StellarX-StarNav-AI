# Dataset Planning

> **Status:** Planning document — no datasets have been downloaded or generated yet.
> This document will be updated as data sources are identified and preparation pipelines are built.

---

## 1. Required Data

The pipeline requires two primary data types:

| Data type | Purpose |
|---|---|
| Star-field images | Training, validation, and testing of the detection and recognition pipeline |
| Star catalog | Reference database for pattern matching and navigation estimation |

---

## 2. Star-Field Images

### 2.1 Real Imagery

Real star-field images from spacecraft or ground-based astronomy instruments provide the most representative data for the system's operating conditions.

**Potential sources:** To be identified during Phase 1.
Considerations include:
- Availability of images with known ground-truth orientation
- Image format and resolution compatibility
- Licensing and usage rights

### 2.2 Synthetic Data Generation

Because real labeled spacecraft imagery with ground-truth orientation may be limited, synthetic star-field image generation is likely to be a primary data source. Synthetic images are generated by:

1. Sampling a spacecraft orientation (attitude)
2. Computing which catalog stars fall within the simulated field of view
3. Projecting star positions onto the image plane using a camera model
4. Applying simulated noise, sensor artifacts, and point-spread function

**Synthetic generation implementation:** To be developed during Phase 3.

**Camera model parameters (focal length, field of view, sensor size):** To be determined.

---

## 3. Star Catalog

The star catalog provides the ground-truth reference against which detected patterns are matched.

### 3.1 Requirements

The catalog must contain, at minimum:
- Star identifier
- Right ascension (RA) and declination (Dec) in a standard epoch (e.g. J2000)
- Apparent magnitude (for brightness-based filtering)

### 3.2 Catalog Source

**Catalog source:** To be determined during Phase 1.
Common candidates for spacecraft star-tracker applications include standard astrometric catalogs filtered to a practical limiting magnitude. The specific catalog will be selected based on coverage, accuracy, and licensing.

### 3.3 Catalog Size and Filtering

The full catalog will be filtered to a subset of bright, well-characterised stars suitable for reliable onboard matching. The magnitude cutoff and number of catalog entries will be determined during Phase 1.

**Image format (FITS, PNG, TIFF, or other):** To be determined based on the chosen data source.

**Catalog format (CSV, HDF5, SQLite, binary):** To be determined. The catalog loader (`src/catalog/catalog_loader.py`) will abstract over the storage format.

The dataset will be divided into three non-overlapping splits:

| Split | Purpose | Approximate proportion |
|---|---|---|

Specific split ratios will be determined once the total dataset size is known.

Splitting strategy must ensure that:

## 6. Preprocessing Steps

Before use, raw data will undergo the following preparation steps:

1. Format conversion to the internal standard (if necessary)
2. Quality filtering (reject images with insufficient star count, severe artifacts, etc.)
3. Background subtraction and noise reduction
4. Normalisation
5. Storage to `data/processed/` in a format ready for the training pipeline

**Specific steps and parameters:** To be determined during Phase 2.

---

## 7. Data Augmentation

To improve model robustness, training data augmentation may include:

- Simulated noise at varying levels
- Simulated star magnitude variation
- Image rotation (if the feature representation is not rotation-invariant)
- Partial occlusion or missing stars
- Simulated sensor artifacts

**Augmentation strategy:** To be determined during Phase 3.

---

## 8. Dataset Limitations

The following limitations are anticipated and should be documented during evaluation:

- **Limited real labeled data:** Ground-truth orientation for real spacecraft imagery is often unavailable, making synthetic data essential but potentially distribution-mismatched.
- **Catalog completeness:** No star catalog is complete at all magnitudes; faint stars may appear in imagery but not be present in the catalog.
- **Sensor variability:** Real sensor characteristics (noise level, point-spread function, dynamic range) vary across instruments; a model trained on one sensor may not generalise to another.
- **Orientation coverage:** The training set must cover the full sphere of possible orientations; gaps in coverage may cause recognition failures.

Specific quantitative characterisation of these limitations will be reported in [`docs/results.md`](results.md) after evaluation.

---

## 9. Data Storage and Versioning

- Raw data is stored in `data/raw/` and is not committed to the repository (see `.gitignore`).
- Processed data is stored in `data/processed/` and is not committed to the repository.
- Star catalog files are stored in `data/catalog/`.
- Dataset versions should be recorded in experiment logs (see [`docs/experiments.md`](experiments.md)).
- Large datasets should be managed with a data versioning tool (e.g. DVC) if needed — to be evaluated during Phase 1.
